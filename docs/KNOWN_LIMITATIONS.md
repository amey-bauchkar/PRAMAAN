# PRAMAAN — Known Limitations, Assumptions & Technical Boundaries

**Principle:** Transparency over overpromising. This document explicitly outlines what PRAMAAN does not do, what assumptions are made, and where external human or legal review is mandatory.

---

## 1. AI & Verification Boundaries

1. **No AI Authorship / Cheating Detection:** PRAMAAN does not claim to detect whether code was written by AI, Copilot, or another human. Git commit timestamps and authorship history are treated as unverified claims. Verification relies exclusively on the student's ability to defend the code in a grounded viva and pass live functional modification probes.
2. **Pure Function Scope for Automated Mutation Probes:** The automated Live Mutation Probe is engineered for pure algorithmic, computational, and utility functions (e.g. data transformations, parsers, core business logic). Complex full-stack applications with external databases or graphical interfaces are verified via code-grounded viva and faculty mentor attestations, not headless container execution.
3. **No Unassisted Model State Promotions:** LLMs never independently transition a skill to `Verified`. The LLM's role in verification is restricted to generating candidate viva questions anchored to specific code spans. The transition itself is driven by deterministic test results or an authorized mentor's signature.
4. **LeetCode & External Coding Profiles:** Until an official enterprise API agreement exists, LeetCode profile evidence is categorized as `external_profile` supporting `Observed` or `Claimed` status only. It never directly awards a `Verified` badge without secondary defense.

---

## 2. Privacy, Regulatory & Legal Boundaries

1. **Regulatory Compliance Status:** While PRAMAAN implements the technical primitives required by India's DPDP Act, NYC Local Law 144, and the EU AI Act (granular consent, purpose limitation, audit logging, impact ratio monitoring, human oversight), it has not undergone formal legal or third-party regulatory certification. Real-world institutional deployment requires review by qualified legal counsel.
2. **Small-Group Suppression Threshold ($N < 5$):** The small-group suppression threshold used in fairness checks is a configurable institutional privacy safeguard, NOT a statutory legal mandate. Institutions may configure this threshold according to their data governance policies.
3. **Protected Demographic Attributes:** Data on gender, category, or caste is stored in a separate, restricted table (`student_group_attributes`) and is accessible exclusively to the batch fairness analysis role. It is strictly excluded from student profiles, search indexes, recruiter visibility, and eligibility rule evaluations.
4. **Minors (Under 18 Years):** Where a student is flagged as a minor (`is_minor = true`), the platform requires an attested guardian consent record before repository indexing or external recruiter sharing can be activated.
5. **OAuth Revocation Scope:** Consent revocation immediately purges stored credentials and withdraws derived evidence in the local database. Remote provider-side revocation (e.g. invalidating the grant at GitHub) requires active `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` credentials; in sandbox environments without these keys, the system executes local token purge and logs `sandbox_inert`.

---

## 3. Placement & Predictive Analytics Boundaries

1. **Provisional Nature of Predictive Placement Models:** Placement forecasting models (AD-03) output cohort-level scenario ranges (e.g. estimated placement rate bands). These are explicitly watermarked and labeled as "Provisional Estimates — Not Statistically Validated." The platform strictly prohibits applying automated negative labels or intervention flags to individual students without TPO review.
2. **Accreditation Data Exports:** Reports generated for NAAC (Criterion 5.2.1) and NIRF formats provide deduplicated placement counts and transparent calculation formulas. These exports are watermarked as "Draft for Institutional Verification" until verified against official university registers.
3. **Synthetic Demo Data:** All demo environments use synthetic tenant data and mock student profiles. Synthetic outcomes are strictly partitioned and can never be merged into real institutional production databases.

---

## 4. Authentication & Infrastructure Boundaries

1. **Client-Side Refresh Token Handling:** In production, Supabase Auth issues short-lived JWT access tokens (typically 1 hour) and refresh tokens. The backend API validates individual access tokens stateless via `jose` and resolves institutional memberships against PostgreSQL. Refresh token lifecycle and silent renewal are managed client-side by `@supabase/supabase-js`.
2. **PostgreSQL Direct Socket vs Pooler Latency:** For serverless and edge container deployments, connections route through the Supabase transaction pooler (port 6543) using `pool_mode = transaction`. Physical connection reuse and `SET LOCAL` context reset have been mathematically proven on this pooler (`db/tests/connection-pool-reuse.test.ts`).
3. **Off-site Audit Log Mirroring:** Database triggers block UPDATE/DELETE on `audit_events`, and the cryptographic hash chain provides tamper-evidence. However, continuous export to an external write-once WORM storage (such as AWS S3 Object Lock) is recommended for high-stakes compliance environments to defend against privileged superusers.
4. **Strict Identity Binding:** Accounts are bound strictly by verified Supabase `sub` UUID claims. Automatic account linking via matching email is deliberately disabled to eliminate external OAuth email collision risks. Account linking must be an authenticated, explicit transaction initiated by an active member.
5. **Runtime Principal Security Boundaries:** The runtime database principal (`pramaan_app_user`) has zero administrative or DDL privileges (`NOBYPASSRLS`, `NOSUPERUSER`, `NOCREATEROLE`, `NOCREATEDB`, `NOINHERIT`). Schema migrations, table creation, and role maintenance must be executed via an out-of-band administrative connection (`DATABASE_URL_ADMIN`) and cannot be executed by the web application pool.
6. **Historical Git Commit Credentials Audit & Rotation:** A plaintext database password was committed in git history in early development commits (`21fa9a7`, `25cd045`). That password was immediately rotated out-of-band via Supabase management channels upon discovery. Migration 007 now uses dynamic role provisioning with zero plaintext secrets. Per strict software engineering audit standards, git history has not been rewritten to preserve commit traceability; the exposed historical credential is completely revoked and non-functional.
7. **Migration Ledger & Schema Evolution:** All database schema changes are strictly recorded in the `schema_migrations` ledger with deterministic SHA-256 checksums. Schema migrations execute exclusively under direct administrative PostgreSQL credentials (`DATABASE_URL_ADMIN`) with persistent session advisory locking (`pg_advisory_lock`) and transactional DDL. Stateless Supabase Management API execution has been permanently disabled due to lack of session locking and transactional DDL atomicity. Fallback to application runtime credentials (`DATABASE_URL`) is strictly prohibited. Reruns are strictly idempotent.
8. **RFC 8785 Canonical JSON Serialization for Audit Hash Verification:** PostgreSQL `jsonb` columns normalize and sort object keys alphabetically upon persistence. In-memory hash computation without key sorting will produce divergent SHA-256 hashes when events are read back from PostgreSQL. PRAMAAN implements RFC 8785 recursive canonical key serialization (`AuditChain.canonicalStringify`) to guarantee cryptographic hash parity between application memory and persistent database storage.
9. **CI Multi-Stage Execution vs Live Supabase Secrets Gate:** In GitHub Actions CI, Job 2 executes full database verification against an ephemeral PostgreSQL 17 Alpine service container using synthetic seeds and isolated test transactions. Live Supabase JWKS asymmetric ES256 verification (Job 3) runs as an environment-dependent gate requiring repository secrets (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`, `DATABASE_URL_ADMIN`). When secrets are unconfigured (e.g. in external PR forks), Job 3 safely skips without failing the pipeline, while Jobs 1 and 2 enforce complete security and invariant compliance.
10. **Forensic Analysis of Migration 009 Historical Audit Record Cleanup (P0):**
    - **Origin of Cleanup:** In initial development commit `0bf87bdf4dcb8d6b4f8850e7055bc9eb3488db4c`, automated integration tests (`db/tests/supabase-real-db.test.ts`, tests 10 and 11) tested trigger-enforced audit immutability on PostgreSQL by inserting synthetic audit records with `action = 'TEST_EVENT', seq = 99999, hash = repeat('a', 64)` under tenant College A (`00000000-0000-0000-0000-000000000001`). Because the tests successfully verified that DELETE operations were blocked by `trg_audit_events_immutable`, those synthetic test artifacts persisted in the shared development database. In subsequent commit `454854ec22a7d51adaf9a224dfe2cea9dccc9344`, the test was refactored to use `seq = 99991` and `action = 'AUDIT_VERIFICATION_TEST'`, cleaning up via superuser trigger disable. However, repeated test runs prior to migration 009 had accumulated duplicate sequence rows for `seq = 99999`. When Migration 009 applied the engine-level unique constraint `uq_audit_events_org_seq (org_id, seq)`, a conditional administrative block disabled `trg_audit_events_immutable` to remove rows matching `action = 'TEST_EVENT' AND seq = 99999`.
    - **Migration 009 SQL Scope & Organization Impact:** The migration cleanup SQL was:
      ```sql
      DELETE FROM audit_events WHERE action = 'TEST_EVENT' AND seq = 99999;
      ```
      This query contained **no `org_id` condition**. While the originating test in `0bf87bdf` targeted College A, the deletion was technically unbounded across all tenants.
    - **Evidence vs Inference Distinction:**
      - *Verified Live Database Evidence:* The live Supabase database contains two organizations: College A (Apex `00000000-0000-0000-0000-000000000001`) and College B (Zenith `00000000-0000-0000-0000-000000000002`). College B's audit chain is 100% intact from `seq = 1` through `seq = 64` originating at `GENESIS_HASH`. College A's surviving audit events begin at `seq = 100000` with `prev_hash = repeat('a', 64)` (60 sequential records from `100000` to `100059`). The exact number of rows deleted by Migration 009 was not logged by the anonymous PL/pgSQL block, and no point-in-time database statement logs or transaction backups are retained from that execution.
      - *Source History Inference:* Commit history confirms that `action = 'TEST_EVENT'` and dummy hash `repeat('a', 64)` were synthetic test artifacts. There is no evidence in source code, schemas, or seeds of real user or production audit events using `action = 'TEST_EVENT'` or `seq = 99999`. However, because row-level execution counts were not captured by the migration script, zero real-data impact cannot be categorically asserted without reservation.
    - **Audit Chain Verification State & Surviving Checkpoint Authenticity:** Under the corrected `AuditChain.verifyChain()` engine, plain unauthenticated `{ seq, hash }` objects and the historical dummy `a*64` hash are rejected as `INVALID`. Checkpoints require strict cryptographic authentication: tenant UUID `orgId` binding, non-negative integer `seq`, and HMAC-SHA256 signature verified against an out-of-band secret key. College A's historical chain in the shared development database is classified as **`UNANCHORED`** (`valid: false`, `isComplete: false`) by default because it starts at `seq = 100000` without genesis block (`seq = 1`). Because no cryptographically signed checkpoint exists for this historical boundary, College A remains strictly `UNANCHORED`. Internal suffix links being valid (`verifySuffixLinks()`) confirms internal integrity but does not authenticate the missing historical prefix (`seq = 1` to `99999`). Complete cryptographic verification cannot be claimed for an unanchored chain. Deleted audit events are not invented or artificially reconstructed.
    - **Applied Migration Immutability Preserved:** In accordance with strict audit standards, Migration 009 has NOT been modified on disk, preserving its exact SHA-256 checksum in the `schema_migrations` ledger. Fresh deployments apply migrations 001 through 010 on a clean database without executing deletions.
11. **Database Integration Test Safety Guards & Tenant Isolation:**
    - Destructive operations and integration tests execute behind an explicit environment guard (`assertSafeTestEnvironment()`) that throws and halts execution if `NODE_ENV === 'production'`, `ENVIRONMENT === 'production'`, or `VERCEL_ENV === 'production'`.
    - Tests are prohibited from inserting synthetic test events into institutional audit chains (`00000000-0000-0000-0000-000000000001` or `00000000-0000-0000-0000-000000000002`). Test suites execute strictly against dedicated disposable fixtures (`TEST_AUDIT_TENANT_ID = 'e0000000-0000-0000-0000-000000000099'`).
    - Teardown in `afterAll` executes within `try ... finally` blocks to guarantee that test audit artifacts are removed and the PostgreSQL immutability trigger `trg_audit_events_immutable` is unconditionally re-enabled even upon test assertion failures.
    - `assertNotInstitutionalTenant(orgId)` protects production institutional records from deletion or mutation by automated test harnesses.
