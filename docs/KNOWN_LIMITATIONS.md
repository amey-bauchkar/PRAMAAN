# PRAMAAN — Known Limitations, Assumptions & Technical Boundaries

**Principle:** Transparency over overpromising. This document explicitly outlines what PRAMAAN does not do, what assumptions are made, and where external human or legal review is mandatory.

---

## 1. AI & Verification Boundaries

1. **No AI Authorship / Cheating Detection:** PRAMAAN does not claim to detect whether code was written by AI, Copilot, or another human. Git commit timestamps and authorship history are treated as unverified claims. Verification relies exclusively on the student's ability to defend the code in a grounded viva and pass live functional modification probes.
2. **Pure Function Scope for Automated Mutation Probes:** The automated Live Mutation Probe is engineered for pure algorithmic, computational, and utility functions (e.g. data transformations, parsers, core business logic). Complex full-stack applications with external databases or graphical interfaces are verified via code-grounded viva and faculty mentor attestations, not headless container execution.
3. **No Unassisted Model State Promotions:** LLMs never independently transition a skill to `Verified`. The LLM's role in verification is restricted to generating candidate viva questions anchored to specific code spans. The transition itself is driven by deterministic test results or an authorized mentor's signature.
4. **LeetCode & External Coding Profiles:** Until an official enterprise API agreement exists, LeetCode profile evidence is categorized as `external_profile` supporting `Observed` or `Claimed` status only. It never directly awards a `Verified` badge without secondary defense.

---

## 2. Privacy, Regulatory & Legal Boundaries

1. **Regulatory Compliance Status:** While PRAMAAN implements the technical primitives required by India's DPDP Act, NYC Local Law 144, and the EU AI Act (granular consent, purpose limitation, audit logging, impact ratio monitoring, human oversight), it has not undergone formal legal or third-party regulatory certification. Real-world institutional deployment requires review by qualified legal counsel.
2. **Small-Group Suppression Threshold ($N < 5$):** The small-group suppression threshold used in fairness checks is a configurable institutional privacy safeguard, NOT a statutory legal mandate. Institutions may configure this threshold according to their data governance policies.
3. **Protected Demographic Attributes:** Data on gender, category, or caste is stored in a separate, restricted table (`student_group_attributes`) and is accessible exclusively to the batch fairness analysis role. It is strictly excluded from student profiles, search indexes, recruiter visibility, and eligibility rule evaluations.
4. **Minors (Under 18 Years):** Where a student is flagged as a minor (`is_minor = true`), the platform requires an attested guardian consent record before repository indexing or external recruiter sharing can be activated.
5. **OAuth Revocation Scope:** Consent revocation immediately purges stored credentials and withdraws derived evidence in the local database. Remote provider-side revocation (e.g. invalidating the grant at GitHub) requires active `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` credentials; in sandbox environments without these keys, the system executes local token purge and logs `sandbox_inert`.

## 3. Placement & Predictive Analytics Boundaries

1. **Provisional Nature of Predictive Placement Models:** Placement forecasting models (AD-03) output cohort-level scenario ranges (e.g. estimated placement rate bands). These are explicitly watermarked and labeled as "Provisional Estimates — Not Statistically Validated." The platform strictly prohibits applying automated negative labels or intervention flags to individual students without TPO review.
2. **Accreditation Data Exports:** Reports generated for NAAC (Criterion 5.2.1) and NIRF formats provide deduplicated placement counts and transparent calculation formulas. These exports are watermarked as "Draft for Institutional Verification" until verified against official university registers.
3. **Synthetic Demo Data:** All demo environments use synthetic tenant data and mock student profiles. Synthetic outcomes are strictly partitioned and can never be merged into real institutional production databases.

## 4. Authentication & Infrastructure Boundaries

1. **Client-Side Refresh Token Handling:** In production, Supabase Auth issues short-lived JWT access tokens (typically 1 hour) and refresh tokens. The backend API validates individual access tokens stateless via `jose` and resolves institutional memberships against PostgreSQL. Refresh token lifecycle and silent renewal are managed client-side by `@supabase/supabase-js`.
2. **PostgreSQL Direct Socket vs Pooler Latency:** For serverless and edge container deployments, connections route through the Supabase transaction pooler (port 6543) using `pool_mode = transaction`. Physical connection reuse and `SET LOCAL` context reset have been mathematically proven on this pooler (`db/tests/connection-pool-reuse.test.ts`).
3. **Off-site Audit Log Mirroring:** Database triggers block UPDATE/DELETE on `audit_events`, and the cryptographic hash chain provides tamper-evidence. However, continuous export to an external write-once WORM storage (such as AWS S3 Object Lock) is recommended for high-stakes compliance environments to defend against privileged superusers.
4. **Strict Identity Binding:** Accounts are bound strictly by verified Supabase `sub` UUID claims. Automatic account linking via matching email is deliberately disabled to eliminate external OAuth email collision risks. Account linking must be an authenticated, explicit transaction initiated by an active member.
5. **Runtime Principal Security Boundaries:** The runtime database principal (`pramaan_app_user`) has zero administrative or DDL privileges (`NOBYPASSRLS`, `NOSUPERUSER`, `NOCREATEROLE`, `NOCREATEDB`, `NOINHERIT`). Schema migrations, table creation, and role maintenance must be executed via an out-of-band administrative connection (`DATABASE_URL_ADMIN`) and cannot be executed by the web application pool.
6. **Historical Git Commit Credentials Audit & Rotation:** A plaintext database password was committed in git history in early development commits (`21fa9a7`, `25cd045`). That password was immediately rotated out-of-band via Supabase management channels upon discovery. Migration 007 now uses dynamic role provisioning with zero plaintext secrets. Per strict software engineering audit standards, git history has not been rewritten to preserve commit traceability; the exposed historical credential is completely revoked and non-functional.
7. **Migration Ledger & Schema Evolution:** All database schema changes are strictly recorded in the `schema_migrations` ledger with deterministic SHA-256 checksums. Schema migrations execute exclusively under direct administrative PostgreSQL credentials (`DATABASE_URL_ADMIN`) with persistent session advisory locking (`pg_advisory_lock`) and transactional DDL. Stateless Supabase Management API execution has been permanently disabled due to lack of session locking and transactional DDL atomicity. Fallback to application runtime credentials (`DATABASE_URL`) is strictly prohibited. Reruns are strictly idempotent.
8. **RFC 8785 Canonical JSON Serialization for Audit Hash Verification:** PostgreSQL `jsonb` columns normalize and sort object keys alphabetically upon persistence. In-memory hash computation without key sorting will produce divergent SHA-256 hashes when events are read back from PostgreSQL. PRAMAAN implements RFC 8785 recursive canonical key serialization (`AuditChain.canonicalStringify`) to guarantee cryptographic hash parity between application memory and persistent database storage.
9. **CI Multi-Stage Execution vs Live Supabase Secrets Gate:** In GitHub Actions CI, Job 2 executes full database verification against an ephemeral PostgreSQL 17 Alpine service container using synthetic seeds and isolated test transactions. Live Supabase JWKS asymmetric ES256 verification (Job 3) runs as an environment-dependent gate requiring repository secrets (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`, `DATABASE_URL_ADMIN`). When secrets are unconfigured (e.g. in external PR forks), Job 3 safely skips without failing the pipeline, while Jobs 1 and 2 enforce complete security and invariant compliance.

## 5. Milestone M2 P0-05 Code Anchor & Evidence Invariants

1. **Client-Supplied Snapshot Boundary & Server-Controlled Provenance:**
   Client-supplied inline snapshots via `/api/evidence/anchors/resolve` or `/api/evidence/snapshots` are permanently non-authoritative (`authoritative: false`, `provenance: 'unverified_client_input'`). They prove content-to-hash correspondence in isolation, but DO NOT prove student authorship, repository provenance, or Git tree history. Authoritative verification (`authoritative: true`) is strictly granted only when a server-side verified ingestion record (`TrustedIngestionRecord`) matching `(orgId, repositoryId, commitSha, studentId)` exists in `ITrustedIngestionStore` (populated exclusively by P0-04 Trusted Static Ingestion). Demanding authoritative verification with a client snapshot fails closed (`UNTRUSTED_CLIENT_SNAPSHOT`).
2. **Production Storage Adapter Prerequisite:**
   In production environments (`NODE_ENV === 'production'`), snapshot registration requires a durable, tamper-evident storage adapter (e.g. S3 WORM / Azure Blob / Supabase Storage with retention lock). The in-memory storage adapter is restricted to development and testing environments; attempting to register snapshots in production without durable storage configured fails closed with `503 DURABLE_STORAGE_REQUIRED`.
3. **AST Parser Scope & Language Grammar Pinned Version:**
   The offline AST parser is strictly implemented for TypeScript and JavaScript using the pinned TypeScript compiler version `5.9.3`. Parsers for Python, Java, C++, Go, and other languages are planned for future M2 milestones. Dynamic parser replacement or execution of third-party plugins is prohibited; all parsers are pinned and registered in `ParserRegistry` keyed by `(parserName, language, parserVersion)`. Zero untrusted code execution occurs during AST parsing.
4. **Universal Purpose-Specific Consent Prerequisite (DPDP Act 2023):**
   Repository analysis, snapshot registration, and AST parsing require an identified trusted student owner (`studentId`) and explicit, active consent under purpose `repo_verification`. This applies across ALL roles: students cannot register snapshots without their own consent; placement officers and platform administrators cannot register snapshots or parse source code without designating the target student and verifying active consent (`STUDENT_OWNERSHIP_REQUIRED`, `CONSENT_REQUIRED_OR_REVOKED`). If the consent service infrastructure is unavailable, resolution and parsing fail closed with `503 CONSENT_SERVICE_UNAVAILABLE`. The `/api/evidence/parse` endpoint outputs diagnostic AST representations only (`diagnosticOnly: true, authoritative: false, provenance: 'diagnostic_parser'`) and cannot create authoritative evidence.
5. **Deterministic Line & Byte Boundary Strictness:**
   Anchor line and byte boundaries are validated with UTF-8 character boundary checks and consistency checks. Boundary offsets that split multi-byte UTF-8 sequences (`INVALID_UTF8_BYTE_BOUNDARY`), contain malformed UTF-8 (`MALFORMED_UTF8_SOURCE`), or have contradictory line and byte ranges (`LINE_BYTE_METADATA_INCONSISTENT`) fail closed as `ANCHOR_INVALID`. Pure line-ending differences (CRLF vs LF) are isolated via `lineEndingMismatch: true`, while whitespace edits are recorded via `whitespaceMismatch: true`, ensuring normalized diagnostics never masquerade as raw integrity failure.
6. **Path Traversal & Buffer Immutability Guarantees:**
   Canonical path validation rejects all relative traversal sequences (`..`), null bytes (`\0`), absolute Unix paths, Windows drive letters, and duplicate directory separators. Memory buffers stored in `InMemorySourceSnapshotStore` are defensively copied on both write and read (`Buffer.from(...)`), eliminating in-process buffer mutation vulnerabilities.
7. **Strict Tenant Partitioning Without Fallback:**
   Snapshot lookups in `ISourceSnapshotStore` (`getSnapshot` and `getSnapshotByHash`) strictly require exact tenant match when an `orgId` is provided. The store never falls back to unscoped snapshots during a tenant-scoped query, completely eliminating cross-tenant disclosure risks from legacy unscoped snapshots. Unscoped lookups are permitted only when invoked with an explicitly unscoped parameter (`orgId: undefined`).
8. **Failure-Safe Registration with Compensating Rollback:**
   Snapshot registration and audit log emission form a failure-safe unit. If newly inserted source code snapshots succeed in storage but subsequent SHA-256 audit chaining throws an unhandled error, `AnchorService` executes a compensating rollback (`deleteSnapshot`) to remove the stored snapshot before rethrowing the failure, guaranteeing that un-audited evidence snapshots can never be persisted or queried.
9. **Student-Partitioned Snapshot Storage and Cross-Student Isolation:**
   Snapshots are partitioned in storage by `${orgId}:${studentId}:${repositoryId}:${commitSha}:${canonicalPath}` and content hash lookups by `${orgId}:${studentId}:${hash}`. Two students within the same college analyzing the same repository/commit have strictly isolated snapshots. `AnchorResolver.resolve()` verifies that student anchors require a matching `snapshot.studentId` (`STUDENT_OWNERSHIP_REQUIRED`), and cross-student mismatches fail closed with `STUDENT_OWNERSHIP_MISMATCH`. Intra-tenant student evidence substitution is physically impossible.
10. **In-Memory Mutex-Serialized Registrations, Conditional Rollback & Leak-Free Cleanup:**
    Concurrent registrations of the same snapshot identity are serialized per identity using an in-memory promise-queue mutex in `AnchorService`. The exact queued promise is retained and matched in `finally`, ensuring the map key is deleted when all queued requests finish without introducing race conditions or leaking memory. Conditional rollback requires `expectedSnapshotId` so that an audit failure in one request only deletes its own snapshot, never deleting a concurrent or pre-existing snapshot (`wasAlreadyPresent === true`). Rollback errors are surfaced with cause preserved (`SNAPSHOT_REGISTRATION_FAILED_WITH_ROLLBACK_ERROR`). Note: The current in-memory mutex serializes within a single Fastify Node.js process; multi-instance clustered API deployments will require distributed locking (e.g. PostgreSQL advisory lock or Redis Redlock) for cross-node serialization.
11. **Mandatory Git Blob SHA for Trusted Snapshots:**
    Snapshots tagged `trusted_ingestion_pipeline` strictly require a valid 40-character Git `blobSha` (`TRUSTED_SNAPSHOT_BLOB_SHA_REQUIRED`). Authoritative resolution fails closed if `blobSha` is missing, malformed, or mismatches the manifest entry. Non-authoritative client/legacy snapshots retain optional blob SHA.
12. **Write-Once Immutability for Trusted Ingestion Records:**
    `InMemoryTrustedIngestionStore.saveRecord` enforces write-once semantics: re-saving an exact duplicate record is treated as an idempotent operation, but any attempt to replace an existing record with a different ingestion ID, tree SHA, owner, or manifest throws `IMMUTABLE_INGESTION_RECORD_MUTATION_REJECTED`. Manifest paths are canonicalized, duplicate canonical paths are rejected (`DUPLICATE_MANIFEST_PATH`), and manifest entries require `blobSha`, `rawFileHash`, and `byteSize`.
13. **Milestone M2 P0-04 Durable Storage Implementation & Production Composition:**
    Milestone M2 Ticket P0-04 has implemented durable snapshot storage (`PgSourceSnapshotStore`), durable write-once trusted ingestion record storage (`PgTrustedIngestionStore`), GitHub credentials repository (`PgGitHubCredentialRepository`), and ingestion jobs (`PgIngestionJobRepository`) backed by Migration 011. In `buildApp()` (`apps/api/src/app.ts`), production mode wires these durable PostgreSQL adapters and fails closed if in-memory adapters are configured in production.
14. **Pre-Persisted Trusted Ingestion Record Requirement:**
    `AnchorService.registerTrustedSnapshot()` requires an already-persisted record in `ITrustedIngestionStore` and will never create or save an ingestion record from its method argument. It strictly verifies all record and manifest fields against the stored record. Client-facing routes cannot create or mutate trusted ingestion records.
15. **Distributed Transaction & Outbox Requirement for Future Durable Adapters:**
    In production environments with external object stores (e.g. S3 Object Lock) and PostgreSQL audit tables, compensating rollback is a best-effort application-layer mechanism. In P0-04, durable PostgreSQL storage with transactional outbox job tracking (`ingestion_jobs`) coordinates between snapshots, records, and audit events.
16. **Explicit Registration Commit State & Fail-Closed Audit Quarantine:**
    Snapshot registration operates under an explicit three-state lifecycle: `pending_audit` -> `audit_committed` (on audit log success) or `quarantined` (on audit log failure). `resolveAnchor(..., { authoritative: true })` strictly enforces that snapshots have `registrationState === 'audit_committed'` (`REGISTRATION_NOT_AUDIT_COMMITTED`). If compensating rollback (`deleteSnapshot`) fails or throws during an audit error, the snapshot remains permanently quarantined in storage and can never be resolved authoritatively.

## 6. Milestone M2 P0-04 Trusted Static Repository Ingestion Boundaries

1. **Pure Static Inspection (Zero Untrusted Execution):**
   The ingestion engine operates strictly as an offline static reader via GitHub REST API (trees, commits, blobs). It NEVER invokes `git clone`, `npm install`, `yarn`, `eval()`, child process execution, or repository package scripts. Repositories containing malicious `package.json` hooks (`preinstall`, `postinstall`) or build scripts cannot execute within the PRAMAAN runtime.
2. **Ingestion Scope & Extension Whitelist:**
   Static repository ingestion is strictly constrained to source code extensions (`.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.cjs`). All binary files, minified bundles (`*.min.js`), package lockfiles (`package-lock.json`), documentation (`*.md`), assets (`*.png`, `*.jpg`), configuration (`.env*`, `*.pem`, `*.key`), Git submodules (`160000`), and symbolic links (`120000`) are rejected or excluded.
3. **Hard Ingestion Size & Resource Limits:**
   To defend against repository zip-bombs and denial-of-service payloads:
   - Maximum file count: 200 files.
   - Maximum individual file size: 512 KB (524,288 bytes). Tree entries declaring size > 512 KB are rejected prior to blob download, and undeclared blobs exceeding 512 KB are excluded post-download.
   - Maximum aggregate retained payload: 10 MB (10,485,760 bytes).
   Exceeding any limit aborts ingestion fail-closed with error details recorded in `ingestion_jobs`. No oversized content is ever persisted.
4. **GitHub Authorization Scope Architecture:**
   - Production Standard: GitHub Apps with fine-grained read-only permissions (`contents:read`, `metadata:read`).
   - Legacy OAuth Fallback: Minimal read-only scopes (`read:user`, `user:email`, `public_repo`). The broad `repo` scope emits an explicit warning. Invalid scopes (e.g., `repo:read`) are strictly rejected. Callback verifies granted permissions fail-closed (`INSUFFICIENT_GITHUB_PERMISSIONS`, 403).
5. **Tenant-Safe OAuth State Consumption:**
   OAuth state consumption runs strictly within `withTenantTransaction(context, ...)` under the restricted `app_api` role with `SET LOCAL app.current_org_id`. PostgreSQL RLS policies on `github_oauth_states` enforce physical tenant isolation, preventing cross-tenant state visibility. Consumption is atomic (`FOR UPDATE`) with immediate single-use invalidation (`used_at = CURRENT_TIMESTAMP`).
6. **Versioned AES-256-GCM Key Ring & Zero-Downtime Rotation:**
   Tokens are encrypted using AES-256-GCM with versioned format `version:iv:tag:ciphertext`. Key rotation maintains past keys in `keyRing: Record<string, string>` allowing existing tokens to decrypt while new tokens use `activeKeyVersion`. Unknown key versions fail closed (`UNKNOWN_KEY_VERSION`), and production mode strictly enforces 64-hex key formatting.
7. **Fixed OAuth Callback URI & Host Header Protection:**
   The server enforces a canonical `GITHUB_OAUTH_REDIRECT_URI` and strict allowlist validation. Client-supplied `redirect_uri` outside the allowlist fails with 400 `INVALID_REDIRECT_URI`. Host headers (`req.headers.host`) and client parameters are never trusted. Production startup fails closed if GitHub credentials or redirect URIs are missing or placeholders.
8. **Request Lifecycle & Durable Tracking:**
   Repository ingestion is executed synchronously within the Fastify HTTP request lifecycle, bounded by HTTP gateway timeouts, while durably tracking state transitions ('queued', 'resolving', 'fetching', 'verifying', 'persisted', 'completed', or 'failed') in the relational `ingestion_jobs` table. This provides immediate client feedback, progress auditability via `GET /api/evidence/repositories/ingest/:id`, and the architectural foundation for a future asynchronous background worker daemon.
9. **Fail-Closed Consent Boundary:**
   GitHub API calls are NEVER executed unless active DPDP `repo_verification` consent is confirmed in `IConsentRepository`. If consent is missing, revoked, or expired, zero API calls are made (`callCount === 0`). Ingestion jobs fail closed with `CONSENT_REVOKED` or `CONSENT_REQUIRED_OR_REVOKED`. Consent is re-checked immediately prior to durable persistence.
10. **Distinct User IDs vs Student IDs in Ingestion:**
    `SessionContext.userId` represents `users.id`. The student database profile is distinct (`students.id`), linked via `students.user_id`. Production endpoints in `apps/api/src/app.ts` resolve `students.id` server-side via `tenantRepo.getStudentByUserId(context, context.userId)` and reject client-supplied `studentId` mismatches fail-closed (`FORBIDDEN_STUDENT_ACCESS`, 403). Foreign keys in `repositories`, `connected_accounts`, `github_oauth_states`, `source_snapshots`, `trusted_ingestion_records`, and `ingestion_jobs` strictly point to `students.id`.
11. **Browser OAuth Callback Architecture:**
    Browser redirects arriving from GitHub without Authorization headers are redirected (302 Found) to the frontend SPA callback route `/integrations/github/callback?code=...&state=...`. The frontend reads the session Bearer JWT and issues an authenticated `POST /api/integrations/github/callback`, preventing token leakage in query strings or browser history while enforcing authentication and audit logging.
12. **Prohibition of Delegated GitHub Connections:**
    Only students may connect their own GitHub identity (`context.role === 'student'`). Placement officers and platform administrators attempting delegated connection are rejected fail-closed with 403 `FORBIDDEN_DELEGATED_CONNECTION`.
13. **Canonical Repository Records & Concurrency Safety:**
    All ingestion jobs, trusted records, and snapshots are bound to canonical database rows in `repositories`, managed by `IRepositoryRepository` (`InMemoryRepositoryRepository`, `PgRepositoryRepository`). Schema migration `012_canonical_repository_unique_constraint.sql` enforces a unique constraint on `(student_id, provider, provider_repo_id)`. Atomic upsert (`ON CONFLICT (student_id, provider, provider_repo_id) DO UPDATE SET ...`) prevents race conditions under parallel ingestion requests and updates `consent_grant_id` when active consent changes. Cross-student repository ID substitution is strictly forbidden (`CROSS_STUDENT_REPOSITORY_FORBIDDEN`, 403). `StaticRepoIngestionService` fails closed if `repositoryRepo` is omitted (`REPOSITORY_REPOSITORY_REQUIRED`).
14. **Public-Repository-Only Scope Architecture & Permission Transparency:**
    OAuth requests use scopes `['read:user', 'public_repo']`. While GitHub's official OAuth specification defines `public_repo` as granting read and write access to public repositories, PRAMAAN application code strictly enforces read-only access (fetching trees, commits, and blobs) and never issues mutating or write requests against student repositories. The OAuth callback verifies that both `read:user` and `public_repo` (or GitHub App permissions `contents:read` and `metadata:read`) are granted, rejecting insufficient scopes with 403 `INSUFFICIENT_GITHUB_PERMISSIONS`. Ingestion of private repositories is rejected fail-closed with 400 `PRIVATE_REPOSITORY_NOT_SUPPORTED`.
15. **Consent Revocation Retention & Snapshot Quarantine Policy:**
    When `repo_verification` consent is revoked in `PgConsentRepository.revokeConsent()`, all `source_snapshots` for the student are atomically transitioned to `registration_state = 'quarantined'`. Quarantined snapshots are immediately inaccessible for authoritative anchor resolution (`REGISTRATION_NOT_AUDIT_COMMITTED` / `CONSENT_REQUIRED_OR_REVOKED`). Pending ingestion jobs are marked failed (`CONSENT_REVOKED`), tokens purged, evidence withdrawn, and skills downgraded. Subsequent re-consent links canonical repositories to the new grant without resurrecting quarantined snapshots; a fresh static ingestion must be executed to verify and register new snapshots.
16. **Preservation of Audit Actor Identity vs Student Owner:**
    Authenticated user identity (`users.id`) and student profile identity (`students.id`) are strictly separated. `SessionContext` supports optional `actorUserId`. Audit events record `actorId = context.actorUserId ?? context.userId` (`users.id`) for both student- and officer-initiated ingestion, guaranteeing accurate audit attribution while snapshots remain owned by `students.id`. Frozen P0-05 resolver invariants remain 100% satisfied.
17. **Browser Callback Deployment Safeguards:**
    Production mode requires `FRONTEND_URL` to be configured with a valid non-localhost URL, failing closed on misconfiguration. Next.js callback component `/integrations/github/callback` implements a `useRef` guard to eliminate double-invocation under React StrictMode development, scrubs temporary `code` and `state` parameters from browser history upon success via `window.history.replaceState`, and explicitly handles GitHub authorization denial errors (`error=access_denied`).
